## 2. What was built

### 2.1 The simulator screen (A, F)
Opened from a survey ("Simulate a journey"), or in one step from "Prototype · not saved" → **Add a demonstration
survey and simulate it**. Three areas, always in this order:

| Area | Contents |
|---|---|
| **Customer** (left) | The synthetic customer picker; "what is on record" with missing values marked; the survey's modules with their status (ran / running / skipped / halted / not reached) and, on a click, **Why did this run? / Why was this skipped?** |
| **The call** (centre) | **What the customer hears**: the module, the question number, the question in large type and the answer control for its type (Yes/No, single choice, multiple choice with its limits and "Other — please specify", free text). **What the engine just decided**: the route taken since the last answer, any condition, any follow-up queue, any module boundary — each with its reason open. **What happens next**: where each possible answer leads, before it is given. The current **follow-up queue** when one is running. The **outcome** card when the call ends |
| **The journey so far** (right) | A timeline grouped by module: one line per thing that happened, with **Why?** on each decision. **Answers and evidence** lists every question of every module that ran and how it stands |

**Controls:** *Give this answer* (the author's own choice), **Step** (this customer's answer), **Back**, **Restart**,
**Play the whole call** (one answer at a time; instant when reduced motion is requested) and *Skip to the end*.

**Comparison:** "Compare with" a second customer shows both journeys side by side, played to the end. A panel states
where they part — "The same for the first N steps, then they part" — with what happened to each and why, and how
their records differ. **Jump to the first difference** brings both columns to that step. No JSON is shown anywhere.

Evidence is progressively disclosed: a line, then its reason and the values read, then "How the result was worked
out" (the condition, part by part) and "Why not another route".

### 2.2 Deterministic execution (B)
`model/sim.ts` runs **the same canonical model the Guided and Graph editors write** — modules, nodes, edges, bindings,
instances and routes. There is no simulator schema: an edit in either editor is in the next run, and Undo changes the
run as well. A run is a pure function of (model, customer record, answers so far); Step and Back are exact.

| Executed | How |
|---|---|
| Module entry conditions | Always / condition (true → runs; false → skipped; unknown → halt for review, or skip with the reason "information missing") / after a named outcome of an earlier module |
| Yes/No and single-choice routing | The route set for the answer; otherwise the route that covers every answer; otherwise the run **stops** |
| Multi-select ordered follow-ups | Queue in configured order, never click order; a question shared by two answers asked once; each follow-up returns to the queue or ends the module; explicit rejoin |
| First-matching-rule priorities | Rules from the top; the first that fits decides; later fits reported, not run; "Otherwise" when none fits |
| Other + specify; free-text validation; selection limits; exclusive answers | The SS-01 stable rejection codes. A rejected answer is recorded and the **same question is asked again** — it can never be skipped |
| Nested AND / OR / NOT; typed answer dependencies | Three-valued evaluation; an answer not collected on the executed route is UNKNOWN |
| MATCH, OTHERWISE and UNKNOWN routes | Each to its own destination; UNKNOWN never falls to "otherwise" |
| Mandatory escalation | Overrides everything else selected; ends with ESCALATE |
| Review-required halts | From a module entry or from a decision's "Stop and flag for review" |
| Named module outcomes and joins | Each outcome follows the survey's route for it: continue, jump ahead (modules in between are "passed over"), or end the call |

**Nothing is bypassed.** A missing destination, a decision with no condition, a module outcome the survey does not
route, a route to a removed step or a loop ends the run as **"The simulator cannot continue"**, names the place, and
offers to open that module in the builder. The simulator never guesses a route.

### 2.3 Explainability (C)
| Requirement | Shown as |
|---|---|
| Which rule was evaluated | The condition as a sentence ("Annual premium is above 12,000 SGD and Sum assured is at least 500,000 SGD"), and the library condition's name and version when it has one |
| Which pinned fields or previous answers were read; the values observed | "What was read": each fact or answer, its value, and whether it was known, missing, answered, answered · nothing selected, left unanswered, or not asked on this path |
| The TRUE / FALSE / UNKNOWN result | In the headline and in "How the result was worked out", part by part |
| The selected route | In the headline: "C1 · cannot be decided (unknown) → the end of the module (Unable to verify)" |
| Why another eligible route was not chosen | "Why not another route": for answers, where the other answers would have led; for conditions, why each other result was not taken; for rules, which earlier rules did not fit and which later ones also fitted |
| Why a module was skipped | "It runs when Product family is ILP. That is false for this customer." — or "…cannot be decided because … is missing … recorded as "information missing", not as "did not match"" |
| Follow-ups queued, deduplicated, interrupted or not asked | The queue line lists each, with the answer that caused it |

**Result: 25 of 25 runs and 7 of 7 rejected answers match** (`fixture_verification.txt`). The reference interpreter
was also re-run and regenerates files identical to the eight fixtures on disk; the fixtures were not changed.

Mapping note: the reference reports a halt on unknown as `blocked: BLOCKED_UNKNOWN` with module status
`BLOCKED_UNKNOWN`; under D-127 / D-134 the simulator names the same event **Review required**. The test maps one name
to the other and compares everything else unchanged.

**Review-required from inside a module** (a decision's "Stop and flag for review") is not covered by an SS-01
fixture; it is verified by the simulator's own tests. So are first-matching rules and the four evidence states. New
fixtures for these belong to SS-03 (§7).

**Guided / Graph equivalence.** A route edited through the Guided operation and through the Graph connection gives
**identical event traces** for the same customer (unit test), and the Chromium journey edits a module in Guided and a
survey route in Graph and runs the same customer before and after.

## 6. One defect found and fixed in earlier code

Changing two view settings in quick succession (for example the customer, then "Compare with") could lose the first
change, because the second was built from the router's not-yet-updated state. The simulator, the module builder's
Guided / Graph switch and the Composer's Blocks / Graph switch now read the address itself. Found by the simulator
journey; the earlier journeys still pass.

## 7. Gaps and honest limits

| # | Item |
|---|---|
| 1 | **It is not the Call360 runtime.** The engine is a browser reading of the SS-01 contract, verified against the fixtures. Parity with the Python controller is a later, separate checkpoint; nothing here may be read as a runtime result |
| 2 | Customers are fixed synthetic profiles. Their records cannot be edited on the screen, and there is no "build your own customer" |
| 3 | Comparison plays both customers with their scripted answers; a hand-answered run cannot be compared yet |
| 4 | A "customer gives no answer" (silence, refusal) turn is not simulated: SS-01 does not yet define its routing. "Left unanswered" appears only for an optional free-text answer left blank |
| 5 | Conditions read answers within one module only (unchanged from SS-02B.1); module entry conditions read the customer record and earlier module outcomes |
| 6 | Entering a module by a jump runs it without evaluating its entry condition — this follows the reference interpreter. It is stated in the trace; whether that is the intended business rule should be confirmed |
| 7 | No fixtures exist yet for: first-matching-rule routing, review-required from inside a module, typed inputs with the four evidence states, the set operators, and the outcome classes. They should be written with SS-03 |
| 8 | Playback speed is fixed; there is no scrubber over the timeline (Back steps one answer at a time) |
| 9 | The simulator runs a survey. A module that is not in a survey (for example the 40-question sample) cannot be simulated on its own |
| 10 | No simulation is recorded or exported; reloading the page discards it (by design for the prototype) |
| 11 | No screen-reader session has been run; structure and labels are verified by inspection, automated scan and the journeys |
| 12 | Wording shown is the synthetic, unapproved question text; delivery (voice, verbatim rules) is out of scope |
| 13 | Moderated usability testing and formal UX sign-off remain the owner's |
