## 1. The two mandatory corrections

### 1.1 Selection limits are never changed silently (D-130)
| Before (SS-02B.1) | Now |
|---|---|
| Adding or duplicating an answer widened the maximum; removing an answer or making one exclusive lowered the limits to fit | **No operation other than the author's own edit changes the limits.** |
| A new multiple-choice question started with stored limits of 1–1 | A question has **no stored limits until the author sets them**; the card says "no limit set, so up to all of them" |
| — | When an edit makes the stored limits impossible, the card shows a **conflict**: what is wrong, that "the limits were kept as you set them", and explicit choices — *Use at least n and at most m*, *Remove the limits*, or type new limits. Routing readiness reports it as something to fix |
| — | Undo restores the previous state exactly: the conflict and the original limits, then the state before the offending edit |

Demonstrated in Chromium (journey "SS-02B.2 corrections", screenshot `GC1`) and in unit tests.

### 1.2 Condition dependencies are stable and typed (D-131)
| Before | Now |
|---|---|
| A condition's earlier-answer input stored a **label** (the question's wording at the time) | An input is a **typed declaration**: the question's stable code, its pinned version, its answer type and its scope. **No display text is stored.** Everything the author reads is looked up when shown |
| Any earlier question could be mapped to an input | Only a placement of the **declared question** can be bound. A different question, a changed answer type, or a compared **answer code that no longer exists** is a validation error |
| A multiple-choice answer was compared with one code | Any / all / none of a **list of stable option codes** (D-125) |
| "Not answered" and "nothing selected" were not told apart | **Not answered = Unknown** for every operator (including "none of"); **answered with nothing selected = a known empty selection**. The sample panel has both states |

Renaming an answer changes the sentence on the card and nothing else; removing it flags the condition
(`GC2`, `GC3`). The exact contract is in `04_SS-01_CANONICAL_CONTRACTS.md` §3.4 and §5.4.

### 1.3 Decisions P-1 … P-5 as applied
| Decision | In the prototype |
|---|---|
| D-125 (P-1) set operators | "includes any of / all of / none of", on option codes |
| D-126 (P-2) first-matching rule | Unchanged behaviour: explicit priority, required fallback, one winner. Rules read the selection just recorded, which is always known; the "never skip an Unknown" rule is recorded in the contract for when rules can read other inputs |
| D-127 (P-3) Stop and flag for review | A governed **Review required** outcome. In a module it is the decision's Unknown route; in the Composer and the survey graph it reads "the call halts · waits for an authorised review · not completed" and is **not a picker** — it cannot be routed elsewhere (`GC4`) |
| D-128 (P-4) mandatory escalation | Only an **approved escalation outcome** is accepted and offered (prototype list: "Escalate" only — synthetic). Checked for every routing mode; a graph connection that would bypass it is refused |
| D-129 (P-5) version upgrades | No propagation. A placement on an older version shows "v2 available · not applied"; upgrading is choosing that version on that placement |

## 2. What was built

### 2.1 Module Question Graph (A)
A second view of the module, switched from the same page (**Guided | Graph**).

| Requirement | As built |
|---|---|
| Yes/No branches; single-choice option-specific routes | One card per question; one line per answer with its destination; an edge per route |
| Multi-select follow-up queues and priority routing | The queue is a **chain in asking order** ("1 · if "Premium"", "2 · if "Benefits" or "Claims"", "then rejoins"); a question shared by two answers appears once. First-matching rules are listed in priority order with "Otherwise" |
| Decision nodes with MATCH / OTHERWISE / UNKNOWN | A quieter dashed card: "When …" and three routes; Unknown is amber and dashed |
| Shared destinations and multiple incoming edges | **Every step is drawn exactly once**, however many routes reach it |
| Named module outcomes | Outcome terminals: one shared "Module ends · Completed"; each exceptional outcome is drawn beside the step that reaches it, so exception lines stay short |
| Mandatory escalation | Red route marked on its row; only an approved escalation outcome can be its destination |
| Clear branch / rejoin visualisation | The normal journey is one straight dark spine; branches hang to the side and return to it |
| Collapsible groups | Each branch and each follow-up queue folds to one stub that still says how many steps it holds, where it rejoins and how many problems are inside. "Show the main journey only" / "Open all branches" |
| Automatic layout | Computed on every change (dagre ranking, then the spine is straightened). "Tidy layout" discards manual moves |
| Zoom, pan, fit-to-view, minimap | Yes. The graph opens at a readable size on the start of the journey, not zoomed out to fit |
| Search and a navigable outline | "Find a question": every step once, in reading order, indented by branch, searchable by number or wording; choosing one selects and centres it. **Available in the Guided view too** (closes keyboard finding K5) |
| Keyboard-accessible alternatives to drag/connect | Selecting a step opens its **own Guided card** in a side panel: every route is set there with the same pickers. Cards are reachable with Tab and selected with Enter |
| Connections never invent rules or bypass validation | A connection calls the existing operation for that route and nothing else. Refused with a reason: a mandatory escalation to anything but an approved escalation outcome; a follow-up question as a destination; "Review required" as an ordinary destination; a step to itself. Anything else that Guided would flag (for example a loop) is flagged identically |

**Editing in the graph:** drag from a route's handle onto a card (the whole card is the drop target); "+" on a route
adds a question or a condition there; the side panel edits everything else. A read-only library module shows the
same graph and refuses edits with the reason.

### 2.2 Survey Module Graph (B)
In the Composer (**Blocks | Graph**). One node per **module instance** with its kind, pinned version, "Runs when …"
sentence and one line per named outcome; questions are not expanded. Edges are the transitions between modules,
jumps and ends of call.

Editing, all through the Composer's own operations and state: **route change** by connecting an outcome to a later
module or to an end of call; **route change, entry condition and reorder** from the side panel (the Composer's own
route control, the same condition drawer, Earlier / Later). Refused with a reason: a route backwards; re-pointing
"Review required". Adding and removing modules stays in Blocks.

### 2.3 One model, one set of operations, one history (C, D)
- Both graphs are **derived** from the one in-memory workspace on every render (`model/graph.ts`); they store nothing.
- A gesture dispatches to the same operations as the Guided pickers and the Composer (`setEdge`, `setRejoin`,
  `setFallback`, `updateRule`, `setDecisionUnknown`, `insertQuestion`, `insertDecision`, `setRoute`,
  `moveInstance`). There is no graph-only rule.
- Stable identifiers throughout (`n…`, `d…`, `r…`, instance ids). An inserted step gets the same id from either view.
- One undo/redo history: an edit made in the graph is undone from Guided and the reverse; demonstrated.
- **Presentation is not semantics:** card positions, zoom, collapse and selection live in the view (and the page
  address), never in the model. Dragging a card changes nothing that is asked; the model fingerprint is unchanged.
- View and selection are kept in the address, so switching views keeps the selected step in view.

## 5. Design decisions made in this checkpoint

| # | Decision | Why |
|---|---|---|
| G-1 | The side panel shows the step's **own Guided card**, not a separate inspector | One editing surface, so the two views cannot drift; it is also the keyboard alternative to drag-connect |
| G-2 | The graph opens readable on the start of the journey; "Fit to view" and the minimap give the overview | A fitted 40-step graph is unreadable; the normal journey should be understandable immediately |
| G-3 | Large modules open on the main journey with branches folded | Progressive expansion; nothing is hidden silently — each stub states its contents, its rejoin and its problems |
| G-4 | Exceptional outcomes are drawn beside their source; "Completed" is shared | One terminal per outcome would pull long lines across the whole graph |
| G-5 | A route is labelled where it **starts** (its row, or just under the card), never mid-line | Mid-line labels landed on other cards |
| G-6 | Several answers to one destination are one edge | Fewer lines; each answer's row still names its destination |
| G-7 | Collapse state is shared between Guided and Graph; positions and zoom are per view and not kept | Collapse is "what I am looking at"; positions are automatic |
| G-8 | Removing a module and adding one stay in Blocks | They carry impact confirmations and the library; duplicating those in the graph adds risk, not capability |

## 6. Points for the owner

| # | Point |
|---|---|
| O-1 | **Availability of earlier answers.** SS-01 (SS-RUL-011) requires a bound answer to be asked on *every* route to the decision. The prototype, following the SS-02B.1 instruction that an uncollected answer "evaluates according to the explicit UNKNOWN policy", also allows an answer asked on *some* routes (marked "not always asked"), and rejects only answers asked on no route. These differ. Options: keep SS-RUL-011 strict; or relax it to "asked on at least one route, with an Unknown policy". Recorded as open in `04` §5.4 (d) |
| O-2 | **The approved escalation outcome set** (D-128) is a synthetic one-item list in the prototype. Its real contents, and who governs it, need a decision |
| O-3 | **Correction to the SS-02B.1 report.** It said first-matching-rule routing was "listed in SS-01 as a future mode" and proposed set operators as new. SS-01 §3.4 already defined `ORDERED_RULES` and §5.1 already listed `CONTAINS` / `CONTAINS_ALL` / `CONTAINS_ANY`. What is genuinely new is `CONTAINS_NONE`, the missing-versus-empty rule and the typed input declaration. The statement in report `12` is annotated |
| O-4 | **Review required** needs its runtime governance (who may resume or close a halted run) defined before simulation or runtime work |

## 7. Gaps and honest limits

| # | Item |
|---|---|
| 1 | A step cannot be created by dragging a connection into empty canvas; new steps come from "+" on a bottom route or from the panel |
| 2 | Routes leaving from the side of a card have no "+" on the canvas (target size); they use the panel |
| 3 | Deleting a step, changing its type or wording, and follow-up queue order are done in the panel card, not by canvas gestures |
| 4 | Manual card positions are not kept between visits or after "Tidy layout"; a structural edit re-runs the layout around them |
| 5 | After a large re-layout the lines can take a moment to appear |
| 6 | At "Fit to view" a 40-question module is an overview only; text is not legible at that zoom |
| 7 | The survey graph does not add or remove modules, and does not draw "waits for an outcome" dependencies as edges (the entry sentence states them) |
| 8 | A module instance's node shows named outcomes, not the questions inside; opening the module is one click from the panel |
| 9 | The canvas's own keyboard support is selection (Tab, Enter) and movement of the view; connecting two cards by keyboard is done in the panel |
| 10 | No screen-reader session has been run on the graph. Cards carry spoken labels and the outline gives a linear reading; this is by inspection and automated scan only |
| 11 | Free-text answers still cannot be condition inputs; conditions still read answers within one module only (SS-02B.1 gaps 2 and 3) |
| 12 | No fixture exists yet for first-matching-rule routing, typed inputs or Review required; they should be added with SS-03 |
| 13 | Everything is computed in the browser by the demonstration evaluator and the prototype's validation; the server remains the authority on a saved revision |
| 14 | Moderated usability testing and formal UX sign-off remain the owner's |
