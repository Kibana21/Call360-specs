## 1. What was built

### 1.1 Internal condition builder (A)
- A **decision point** is a step of a module that asks nothing. It can be added anywhere a question can: from any
  "+" on a path (before a question, at the start, before the module's end) and from any destination picker
  ("Or create … Condition" — after an answer, or on a decision's own route).
- Every decision has **three results, each with its own explicit destination**: *Matches*, *Otherwise*, *Unknown*.
- **Safe insertion**, as for questions: on an existing route only *Otherwise* inherits the former destination;
  *Matches*, *Unknown* and the condition itself start undecided and are flagged. Nothing is invented.
- The Guided Builder shows a **compact decision card**: its number (C1, C2 …), the condition as one sentence, and
  three aligned destination pills. The card is deliberately quieter than a question card (dashed, tinted, no
  shadow), because it is not something the customer hears.
- The rule tree is **not on the canvas**. Clicking the sentence opens the same contextual drawer used for "when does
  this module run?" (the SS-02A.2 modal drawer: focus trap, Escape, focus restoration).
- Questions on a decision's branch are numbered after the question the decision follows (a decision after Q1 leads to
  Q1a), so numbering still reads as a sequence of things asked.

### 1.2 Reusable and parameterised conditions (B)
| Requirement | As built |
|---|---|
| Create a reusable condition | In the drawer: build it, tick "Also add it to the reusable library", name it |
| Use an existing reusable condition | "Library condition" → choose; its definition is shown as a sentence with its named settings in brackets |
| Named parameters per placement | A numeric value can be made a **named setting**; each placement fills in its own value. One definition, different values, different verdicts |
| Typed fields and compatible operators | Money / whole number: at least, above, at most, below, exactly. List and yes/no fields: is, is not. Single-answer question: is, is not. Multiple-choice question: includes, does not include. The comparison is kept when the field changes and still applies |
| Nested AND / OR / NOT | Groups "All of these" / "Any of these" / "None of these", nested to three levels |
| Version identity | Every condition has a code and version; a decision card shows "Large commitment · v1"; the library lists each version with where it is used |
| Preview with sample values | "Try it with sample values": customer details and earlier answers, each of which can be set to missing / not answered; the verdict is explained line by line |
| Impact awareness | "Change what this condition checks…" first lists **every consumer** (module entry rules and decision points, in every module, with the version each uses, and "this placement" marked) |
| Definition versus binding | Two visibly separate zones: **The condition — shared definition** (locked) and **For this placement — changes nothing elsewhere** (values and answer mapping) |
| No silent change to another consumer | A library condition cannot be edited in place. The author chooses **a new version for this placement** or **a separate condition**; every other consumer keeps the version it has. Verified in the journey and in unit tests |

### 1.3 Earlier answers as inputs (C)
- The drawer's "What is known at this point" lists, for the decision being edited: answers **always asked before
  it** (every route passes through them) and answers **asked on some routes only**.
- A condition reads an earlier answer through a **named input**; the placement maps that input to a question.
- Only answers that can exist at that point are offered. A mapping that points to a later, removed or unreachable
  question is a **validation error** ("reads the answer to …, which is not asked before it") — it never looks valid.
- An answer that was not collected evaluates to **Unknown** under three-valued logic and follows the decision's
  Unknown route. It is never read as "no". Deleting a question that a condition reads leaves the input unmapped and
  flagged, not silently dropped.

### 1.4 First-matching-rule routing for multiple choice (D)
- A third routing mode on multiple-choice questions, **"First matching rule"**, beside the preserved
  "Everybody continues" and "Follow-ups for each answer".
- Each rule: **priority** (its place in the numbered list, changed with move-earlier / move-later), **match
  criteria** ("includes any of / all of / none of" + the answers), and a **destination**.
- **"Otherwise"** is the explicit fallback when no rule fits. It is required.
- Exactly **one** route is taken. Rules that also fit but come later are reported as "also fits, not used"; there is
  no parallel execution.
- A selection that breaks the question's limits is **not routed at all** (the question is asked again); this is
  stated on the card and shown in the preview.
- "Try a combination" shows which rule decides for a sample selection, the destination, and which later rules also
  fitted.
- A rule that can never decide (an earlier rule always fits first, or no allowed selection fits it) is marked.
- **Mandatory escalation is respected:** if any allowed selection containing a "Must escalate" answer would end
  anywhere other than an escalation outcome, it is a validation error on that answer.
- Switching to this mode keeps the question's former destination as the fallback and invents no rule.

### 1.5 Multi-select validation (E)
- **Minimum and maximum are editable** on the card, in one sentence: "The customer chooses at least [1] and at most
  [3] of the 4 answers that can be combined."
- Inline validation: minimum above maximum; maximum above the number of combinable answers.
- A plain-language **example** under it, built from the question's own answers: what is accepted, what is not, and
  that an exclusive answer can only be chosen on its own.
- Exclusive answers, "Other — please specify" and mandatory escalation keep the SS-02A behaviour. Removing an answer
  or making one exclusive fits the limits to what remains. An exclusive answer chosen with others is now reported
  before the count limit, because it is the more specific reason.

### 1.6 UX (F)
- Plain-language summaries everywhere a condition appears: the decision card, the module card's "Runs when …", the
  drawer's headline sentence, the library, and a folded question ("5 options · 3 rules, the first match decides ·
  otherwise → …").
- The owner's example reads on the canvas exactly as: **"When Annual premium is above 12,000 SGD and Sum assured is
  at least 500,000 SGD"** → *Matches* → the additional affordability question.
- Complex editing appears only on request (the drawer; the rule list only in rule mode; "Try a combination" folded).
- No change was made to the accepted question-card design other than the two additions this checkpoint requires (the
  selection-limits sentence and the third routing mode on multiple-choice questions).

### 1.7 One canonical model (G)
- Decisions are nodes of the **same module graph** and are routed by the **same edges** (`MATCH`, `NO_MATCH`,
  `UNKNOWN`) as in SS-01. Rules and the fallback live in the question node's routing, like follow-ups.
- Every edit is one pure operation on the one in-memory workspace; the Guided view is derived and stores nothing, so
  the future Graph view can use the same operations. There is no separate condition model for either view.
- Stable identifiers: question nodes `n1…`, decision nodes `d1…`, rules `r1…`, conditions `code@version`. Display
  numbers (Q1, C1) are derived and may change; identifiers do not.
- Undo and redo cover every condition, binding, route, rule and limit edit, each as one step.
- Evaluation is deterministic (three-valued logic; first matching rule). It is the prototype's demonstration
  evaluator and is labelled as such; no parity with the backend is claimed.

## 4. Prototype contract notes (G: "document any prototype contract changes")

The prototype keeps the SS-01 semantics. Its in-memory shape differs from the canonical JSON in these ways; the F6
unit test contains the exact translation and proves the results agree.

| Topic | SS-01 canonical contract | Prototype shape | Kind |
|---|---|---|---|
| Decision's unknown policy | `unknown_policy: "ROUTE_UNKNOWN"` | `unknownPolicy: 'ROUTE'`; `'BLOCK'` = stop and flag for review (no Unknown edge) | Naming only. `BLOCK` on a decision is the D-118 policy already used for module entry |
| Answer input binding | `inputs: { name: { answer: { node } } }` | `inputs: { name: { node } }` | Shape only |
| Condition input declaration | `inputs: { name: { type: OPTION_CODE, option_set } }` | `inputs: { name: { label } }`; the type comes from the mapped question | **Simplification.** The canonical typed declaration is needed in SS-03 so that a reusable condition can be checked against the question it is mapped to |
| Node, edge and module keys | `node`, `edge`, `normal_answer` | `id`, `id`, `normal` | Naming only |
| Comparison operators | EQ, NEQ, GT, GTE, LT, LTE | plus `INCLUDES` / `EXCLUDES` for a multiple-choice answer | **Proposed addition** — see P-1 |
| First-matching-rule routing | Listed in SS-01 as a future mode | `routing.mode: 'ORDERED_RULES'`, `rules: [{ id, kind: ANY/ALL/NONE, options, to }]`, `fallback` | **Proposed contract** — see P-2 |
| Rule and fallback routes | — | Stored on the node's routing (as follow-ups are), not as edges | Prototype choice; see P-2 |

### Proposals for the owner (not decisions; nothing in SS-01 was changed)
| # | Proposal | Why |
|---|---|---|
| P-1 | Add set operators (`INCLUDES`, `EXCLUDES`) to the condition contract for multiple-choice answers | Without them a condition cannot read a multiple-choice answer |
| P-2 | Add `ORDERED_RULES` to the canonical routing contract as built here: ordered rules, required fallback, one winner, invalid selections not routed | The owner asked for first-match routing; this is the smallest contract that expresses it. Whether rules are stored as edges (`on: RULE:<id>`) or on the node is an SS-03 schema question |
| P-3 | A decision's "Stop and flag for review" needs a defined run result in SS-01 terms (a blocked run, not a module outcome) | The prototype shows it as a destination choice; the runtime meaning must be fixed before simulation (SS-02B.3) |
| P-4 | Mandatory-escalation rule for `ORDERED_RULES`: every allowed selection containing a mandatory answer must end with an outcome other than Completed | It is how the prototype applies D-122 to this mode; it should be confirmed as the rule |
| P-5 | Upgrading other consumers to a new condition version is a separate, deliberate action (per consumer, with a preview of what changes) | The prototype only ever moves the placement being edited; there is no "upgrade the others" action yet |

No new fixture was added. A fixture for first-matching-rule routing should be written when P-2 is decided.

## 5. Gaps and honest limits

| # | Item |
|---|---|
| 1 | A reusable condition that reads earlier answers stores only a label for each input, not its type (see §4). Mapping it to a question with different answers is not yet checked |
| 2 | The builder offers earlier answers of choice questions only; free-text answers cannot be read by a condition |
| 3 | Conditions read answers from the **same module** only. Reading an answer from an earlier module of the survey is not built (it needs the survey-level availability analysis; planned with the graph work) |
| 4 | Rules use any / all / none of a set of answers. A rule cannot yet combine answers with customer details; that would be a decision point after the question |
| 5 | In rule mode a new question cannot be created from a rule's destination picker (existing steps and outcomes only); in the other modes it can |
| 6 | "Never decides" and the mandatory-escalation check enumerate allowed selections; they are skipped for questions with more than 12 answers |
| 7 | No "upgrade the other places to the new version" action (P-5), and no side-by-side comparison of two versions |
| 8 | Named settings exist for numbers only; a list value (for example the product family) is always fixed in the definition |
| 9 | Cycles through decision routes are detected and reported, as for questions; there is no visual of the loop until the graph view |
| 10 | Library modules are still read-only when opened from Home; a decision in one can be inspected but not edited without "Edit a copy for this survey" |
| 11 | Display numbers still change when routes change (SS-02A.2 gap 8); branch questions under a decision share the letters of the question before it |
| 12 | The drawer for a nested AND / OR / NOT is long on a 900 px-high screen; it scrolls inside the drawer |
| 13 | No screen-reader session has been run; semantics are correct by inspection and automated scan only |
| 14 | Everything is computed in the browser by the demonstration evaluator. Real validation and evaluation are the server's, on a saved revision |
| 15 | Moderated usability testing with business authors and formal UX sign-off remain the owner's |
