## 1. Jump versus module entry condition (D-135)

### 1.1 The rule
The previous behaviour — a jump entered its target "unconditionally" — is **withdrawn** (it came from SS-01 §2.2 and
the reference interpreter). Three things are now kept apart:

| Concept | Decides | In the model |
|---|---|---|
| **Routing / jump** | which module is the next *candidate* | the sequence; an outcome route to a module; a skip disposition to a module |
| **Activation trigger** | *when* a module is selected | in sequence; by a jump; or only by a named earlier outcome ("After an outcome") |
| **Eligibility condition** | whether the candidate *may execute* | the module's condition, with its explicit UNKNOWN policy |

For a jump target:

| Eligibility | What happens |
|---|---|
| TRUE, or no condition | It runs |
| FALSE | Skipped, with its reason; then the **skip disposition** configured on that module |
| UNKNOWN | Its explicit UNKNOWN policy: *stop for review* → a missing-information halt; *skip and record why* → skipped as "information missing", then the skip disposition |
| No UNKNOWN policy, or no skip disposition | **Validation failure.** If run anyway, the run ends as an invalid draft. Nothing is invented |

**Skip disposition** is a new member of a module instance (`if_ineligible` in the contract): continue with the next
module, go to a later module (whose own eligibility is then checked), or end the call with an outcome. It is
required only where it can matter — a module that a jump can reach **and** that has an eligibility condition — and is
used only after a jump. A module skipped in sequence behaves as before: the next module is considered.

**No re-entry, no loops:** every move is to a later module and each module is considered at most once in a run; a
backward route or disposition is a validation error and stops a run.

**Activation by a named earlier outcome is preserved** and still works exactly as before in sequence.

### 1.2 Where it was changed
| Place | Change |
|---|---|
| Canonical contract | `04` **§2.2a** (withdraws "entering it unconditionally"; defines the three concepts, the table above, `if_ineligible`, the validation codes, the trace) |

### 1.3 Eligibility and activation in the authoring UI — without loading the Lego cards
- **Cards are unchanged**, except that the one kind of card where it matters — a module that a jump can reach and
  that has a condition — gains one row under its outcomes: **"Jumped to, but does not apply → …"**, a route picker
  like the others. In the demonstration survey that is one card out of eight.
- The **condition drawer** states which of the two the author is setting: *"**Eligibility.** This decides whether
  the module may run when the survey reaches it — in sequence or by a jump. A jump only selects the module; it never
  bypasses this."* or *"**Activation.** This decides when the module is selected: only after the earlier module ends
  that way, or when another module jumps to it. It is not a condition on the customer."*
- The **survey graph** shows the disposition as a route of its own ("If it does not apply") that can be connected,
  re-pointed and disconnected like any other, through the same operation as the card.

## 2. Review-required and blocked semantics (D-136)

### 2.1 Six terminal states, never merged
| State | What it is | In the simulator |
|---|---|---|
| **Completed run** | Every module that applied finished | "The call is completed" |
| **Ended with an outcome** | A named outcome was routed to end the call — an exception, or an escalation reached by ordinary routing | "The call ends: Unable to verify" — "classified as an exception, not an escalation" |
| **Mandatory escalation** | The call ended with an escalation outcome *because a mandatory-escalation answer was given* | "The call ends: Escalate — mandatory escalation" |
| **Governed REVIEW_REQUIRED outcome** | A module **ran and ended with** "Review required" (a decision set to stop and flag for review) | "Halted — review required"; the module shows "Ran · Review required" |
| **Missing-information review halt** | A module's **eligibility** could not be decided and its policy is to stop. The module never started: there is no module outcome | "Halted — information is missing"; the module shows "Halted · information missing" |
| **Invalid or incomplete draft** | The draft cannot run past a point. Not a result of a call | "This draft cannot run past here" — "Nothing was decided and nothing is guessed" |

Both halts leave the run pending an authorised review and not completed, and say so; they are still two different
states with different evidence. An escalation reached by an ordinary route is *not* reported as a mandatory
escalation. Contract: `04` **§2.2b**.

### 2.2 The fixture mapping, made explicit and versioned
In SS-02B.3 the simulator's test compared a halt with the historical fixtures' `blocked: BLOCKED_UNKNOWN` by quietly
renaming it. That is replaced:

- The **engine keeps its six states**; it no longer produces a "blocked" result at all.
- The **historical fixtures (schema `/1`, F1–F8) are unchanged** — regenerated by their reference interpreter and
  compared byte-for-byte.
- **New fixtures use schema `/2`** (G1–G6) with the six states and module status `HALTED_MISSING_INFORMATION`.
- The `/2` → `/1` mapping is **stated once** (`04` §2.2b, `fixtures/README.md`) and applied by one named function in
  the test, outside the engine. It is one-way and partial: `/1` has **no equivalent** of the governed
  `REVIEW_REQUIRED` outcome, and the mapping refuses to translate it rather than fold it into "blocked". `/2`
  comparisons use no mapping.

## 4. No-answer behaviour — recorded, not built (D-137)

Recorded in `04` **§5.5** as an open requirement. **Nothing was implemented and no runtime behaviour was invented.**
The prototype has no "no answer" turn; its only related state is `UNANSWERED` for an optional free-text answer left
blank.

| # | Outstanding requirement |
|---|---|
| NA-1 | Silence / timeout — how long, measured from what, recorded as what |
| NA-2 | Customer refusal — an answer, a non-answer or its own state; for which questions it is acceptable |
| NA-3 | Retry and repeat limits — per question and per call; whether a repeat must use the approved wording |
| NA-4 | Escalation or termination policy when the limits are reached — and the catalogued outcome it uses |
| NA-5 | Explicit evidence that a question was not answered — attempts, times, delivery made, reason |
| NA-6 | Routing of a non-answer — a route key, a node policy or a default; what a condition reads |
| NA-7 | Interaction with mandatory questions, follow-up queues and mandatory escalation |
| NA-8 | Lifecycle events that resemble non-answers (dropped call, call-back request, agent takeover) |

**Contract decisions needed before backend implementation:**
1. The evidence model for an unanswered question: states, reasons, attempts.
2. Whether a non-answer is a route key, a node-level policy or a lifecycle event — and its place in selection
   precedence (`04` §2.3).
3. Retry limits, and who sets them: the question, the module, the survey or the channel.
4. The catalogued outcome or outcomes for "could not obtain an answer", and their class.
5. What conditions and module eligibility read for a non-answer (today an unanswered input is UNKNOWN).
6. Golden fixtures for each of the above.

## 7. Points for the owner's approval

| # | Point |
|---|---|
| A-1 | **A jump to a module that is "activated after an outcome".** Such a module has an activation trigger and no eligibility condition. I have taken a jump to be an explicit activation, so the module runs. The alternative — a jump does not satisfy an outcome trigger — is equally implementable. Please confirm (`04` §2.2a) |
| A-2 | **A module cannot have both an activation trigger and an eligibility condition** in the current contract (one `entry`). If a module should be "activated after outcome X **and** only if eligible", the entry needs two parts. That is a schema decision for SS-03 |
| A-3 | **Skip disposition only after a jump.** A module skipped in sequence still simply lets the next module be considered. If a module skipped in sequence should also be able to end the call or go elsewhere, the disposition should apply there too |
| A-4 | **Mandatory escalation at survey level.** A module that ends with an escalation outcome because of a mandatory answer can still be routed by the survey to "continue". Module-level routing is protected; the survey-level route is not yet validated. A rule such as "an escalation outcome may only end the call or go to an escalation module" needs your decision |
| A-5 | **The no-answer decisions** of §4 |
