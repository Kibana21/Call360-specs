## S3-A design and decisions (D-71, D-73 approved 2026-11-18; D-70, D-72, D-74, D-75 awaiting confirmation)

- **D-70 Evaluation methods.** The approved expected-answer policies (`EXACT_BOOLEAN`, `ACKNOWLEDGEMENT`,
  `NUMERIC_MATCH_POLICY_FACT`, `NARRATIVE_REVIEW`, `COLLECT_ONLY`; SCRIPT_GOVERNANCE "Answer is not only YES/NO") are
  kept unchanged, and three structured methods are added under the authorised list: `NUMERIC_COMPARE` (number vs an
  approved value with operator `EQ/GTE/LTE/GT/LT`), `ENUM_MATCH` (choice is one of the approved accepted options — exact
  value comparison) and `ENUM_MATCH_POLICY_FACT` (choice equals a mapped enumerated policy fact). Capture-only =
  `COLLECT_ONLY`; human assessment = `NARRATIVE_REVIEW`. Each method is valid only for its answer type.
- **D-71 Approved fact mappings.** `premium_term_years` (numeric, YEARS) and `premium_amount` (numeric, in the
  snapshot's `currency`; SGD only, Singapore-only) were already approved in S2; **`premium_frequency` (enumerated) is a
  new mapping** of an existing snapshot fact — please confirm. A choice question mapped to it may only offer approved
  values of that fact.
- **D-72 Units.** Governed list `YEARS`, `MONTHS`, `SGD`, `COUNT`. Only the definitional conversion YEARS → MONTHS (×12)
  is applied; any other mismatch (e.g. a MYR fact for an SGD answer) is `MISSING_EXPECTED_FACT`, never a guess.
- **D-73 Tolerance.** No tolerance or threshold is assumed: the default is exact. A tolerance is allowed only with an
  `EQ` comparison and only with the reference of its business approval (3–120 characters); it is part of the question
  revision and so passes maker-checker review. Bounds are inclusive. The demo and tests use synthetic references only
  (e.g. `SYN-TOL-001`); no real tolerance has been approved.
- **D-74 Results and meaning.** `MATCH`, `MISMATCH`, `UNRESOLVED` (presented but no usable answer: unclear after the
  approved re-prompts, refused, unknown, not delivered), `NOT_ASKED` (applicable, never presented — e.g. after
  termination), `MISSING_EXPECTED_FACT`, `NOT_APPLICABLE` (excluded by an approved condition), `NOT_EVALUATED`
  (capture-only questions and lifecycle statements) and `HUMAN_ASSESSMENT_REQUIRED`. Each result also carries the
  equivalent seeded S0 `rule_evaluation` value (MATCH / MISMATCH / INDETERMINATE / NOT_EVALUATED). **A MATCH is not a
  compliance PASS and a MISMATCH is a discrepancy for review — not a finding, breach, severity or case decision.**
  Controller completion and answer evaluation are reported separately.
- **D-75 Where evaluations live in S3-A.** Simulation only: interactive runs → insert-only
  `simulation_answer_evaluation`; scenario runs → inside the insert-only `simulation_result`. Operational
  `rule_evaluation` rows (used by S0 KPIs) are not written; evaluating real sessions requires separate authorisation.
  *(Wording revised and approved by the owner 2026-11-18.)*

## S3-A as built (2026-11-18) — IMPLEMENTED AND VERIFIED, awaiting owner acceptance

**Engine** (`app/domain/answer_evaluation.py`, engine `call360.answer-evaluation/1 (S3-A deterministic)`): pure — no
database, clock, randomness or model. `configure()` validates an authored rule (answer-type compatibility, governed
operators and units, approved fact mappings, tolerance with approval reference, accepted options ⊂ question options,
"accept every option" refused) and returns the stored form; `rule_of()` reads a question revision from frozen content
(legacy S0/S2 `NUMERIC_MATCH_POLICY_FACT` rules get exact defaults); `evaluate(content, controller, fact_source)`
evaluates every planned item in plan order from the controller's final item states and last answers. Decimal
arithmetic; deterministic output. Each result: question code, question revision id and number, method, rule data and
plain-language rule, original structured answer, normalised answer, expected value with its source
(`RULE` or `POLICY_FACT:<key>`, fact value, unit conversion), result, explanation, S0-equivalent result, stage, role.

**Script Studio** (`script_authoring.normalise_question` → `answer_evaluation.configure`): the structured rule is stored
in the existing `question_revision.expected_value` JSON (operator, value, unit, tolerance, tolerance reference, accepted
options) and the fact mapping in `policy_fact_key` — no column added to seeded tables, so seeded content and its digest
are unchanged. Editor: "Evaluation method" (only methods valid for the answer type), "Evaluation rule" fieldset
(policy fact — filtered to numeric or enumerated facts, comparison, expected value, unit, tolerance, tolerance approval
reference, accepted options) and a plain-language "Evaluation rule:" line on every question (draft editor and
read-only view). Validation messages come from the server. Maker-checker, immutable published versions and question
revisions are unchanged: a rule change is a new question revision, visible in the version diff and in workbench
comparisons.

**Migration `0022_answer_evaluation`**: widens three CHECK constraints on `question_revision` (policy vocabulary; fact
key required exactly for the two fact methods; expected value required for value methods) — no row touched; creates
insert-only `simulation_answer_evaluation` (run, events evaluated + SHA-256, script version, content SHA-256 and source,
policy fact snapshot id + SHA-256, engine version, input digest — unique per run, controller status / outcome, results,
totals, actor). Downgrade refuses if evaluations or new methods exist. Applied to `call360_test` and to development
`call360` (backup `~/call360-backups/pre_s3a_20261118_081100/`).

**Interactive evaluation** (`app/domain/simulation_evaluation.py`; `POST/GET /api/v1/script-simulations/{run_id}/evaluations`,
`GET …/evaluations/{evaluation_id}`; write `script.simulate`, read `case.read` + `script.read`; CSRF, rate limit,
audit `SIMULATION.ANSWERS_EVALUATED`): evaluates the run's recorded events as they are now (in progress or ended)
against the exact content the run used (the draft's content snapshot for a version test, the frozen published manifest
otherwise) and the run's pinned policy fact snapshot — never the mutable policy record. Identical inputs return the
existing record (`created: false`); new answers create a new evaluation and earlier ones are kept. Every read re-derives
the results from the stored inputs and reports `replay.matches`.

**Simulation Workbench**: "Answer evaluation" card on interactive runs (evaluate, totals, "The conversation completed,
but the answers contain N mismatches and M unresolved answers", table of question · expected value · actual answer ·
method · result with an explanation row and per-question evidence, evidence trace with engine, content, snapshot,
events and input digests and the replay check; earlier evaluations selectable). Scenarios: facts gain
`premium_term_years`, `premium_amount`, `currency` (SGD) for the fact mappings; expectations gain per-question
`evaluations` and `basis` (`INDEPENDENT` / `GENERATED_BASELINE` — S2-E acceptance condition); dry runs and results show
the evaluation table; failures explain evaluation differences ("Q-X answer evaluation: expected mismatch, got match —
…"); coverage lists evaluation results observed per question; comparisons list evaluation-rule changes and evaluation
result differences per scenario.

**Isolation**: no contact attempt, session, survey run, answer observation, rule evaluation, finding, hold, case state,
assignment or KPI input is written (asserted before / after in the API test and the Playwright journey).

## S3-B design and decisions (proposed — need owner confirmation)

- **D-76 Finding classes and categories.** Each evaluation outcome that can trigger a finding has a fixed,
  system-defined class: MISMATCH → **customer discrepancy**; UNRESOLVED and NOT_ASKED → **missing evidence**;
  MISSING_EXPECTED_FACT → **system-data issue**; HUMAN_ASSESSMENT_REQUIRED → **human assessment**. MATCH, NOT_EVALUATED
  and NOT_APPLICABLE never trigger. Categories are the S0 finding taxonomy plus two new values, `POLICY_DATA_ISSUE` and
  `NARRATIVE_REVIEW`, and each trigger allows only: MISMATCH → FACT_MISMATCH, UNCLEAR_UNDERSTANDING, DISCLOSURE_CONCERN,
  CONTRADICTORY_ANSWER; UNRESOLVED → MISSING_MANDATORY_ANSWER, UNCLEAR_UNDERSTANDING; NOT_ASKED →
  MISSING_MANDATORY_ANSWER; MISSING_EXPECTED_FACT → POLICY_DATA_ISSUE; HUMAN_ASSESSMENT_REQUIRED → NARRATIVE_REVIEW,
  DISCLOSURE_CONCERN.
- **D-77 Rule scope and precedence.** A rule applies to one question, to the questions linked to one compliance control
  (from the frozen script content), or to any question (optionally mandatory only), for one trigger. The most specific
  level wins (question, then control, then any); every rule at that level produces its own finding — nothing is chosen
  arbitrarily. Two rules with the same scope, target and trigger are rejected as ambiguous. A triggering outcome that no
  rule covers is reported as **not converted** and produces no finding (not every mismatch is a finding).
- **D-78 Severity and review.** Severity (LOW / MEDIUM / HIGH / CRITICAL; compliance finding severity, not SBQ risk) comes
  only from the rule, which must state a justification (10–300 characters); there is no default. Human review is
  configurable per rule and always required for human-assessment items. No finding is a breach determination.
- **D-79 Governance.** Finding rule sets are versioned per market (one open and one published version), edited by
  authors with `script.edit`, approved by a different checker with `script.approve` and published by a checker who did
  not author it with `script.publish` (the Script Studio separation of duties). Published versions are immutable
  (service and database guard); superseded versions are kept. All rules are synthetic development configuration
  (`SYNTHETIC_UNAPPROVED`).
- **D-80 Where findings live in S3-B.** Simulation only: interactive runs → insert-only `simulation_finding_set` /
  `simulation_finding`; scenarios → inside the insert-only `simulation_result`. The operational writer
  (`persist_operational`) exists for later use with real callback evidence, refuses non-synthetic cases, has no API
  and was exercised only on a seeded synthetic fixture in the test schema. No real voice session is evaluated.

- **D-81 Dispositions** (S0 finding statuses only; nothing new): START_REVIEW OPEN→UNDER_REVIEW; CONFIRM
