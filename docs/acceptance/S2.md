## S2-A as built (2026-11-17)

**Model reuse.** The S0 model is unchanged in shape: `script_family` → `script_version` → `script_section` (position,
inclusion condition) → `script_module` → `module_question` → immutable `question_revision` of a stable
`question_bank_item`; controls via `control_mapping`. Migration `0015_script_authoring` only:
- activates `script.edit` (USER) and `script.approve`/`script.publish` (new `SC_CHECKER` role, group
  `LOCAL_SC_CHECKER_SG` → SG scope, audited like the seeded scope mappings);
- revises `script_version_guard`: a version may be submitted and approved with its own new modules still DRAFT (so the
  checker reviews content before anything is published), and every module must be PUBLISHED before the version is
  PUBLISHED or SCHEDULED; all other S0 rules stand (content frozen once a version leaves DRAFT, maker ≠ reviewer,
  valid manifest and checksum required). Downgrade restores the 0005 guard exactly;
- adds `script_draft_module_lock`: a DRAFT module belongs to one version and is frozen while that version is submitted
  or approved (enforced in the database, not only the API);
- adds the insert-only `script_change_event` table (version, sequence, event type, actor, reason, details).

**Authoring rules (backend, `app/domain/script_authoring.py`).** Only DRAFT content changes. Every change checks the
draft's `row_version` (a stale editor gets `409 STALE_DRAFT`, nothing is overwritten), bumps it, resets validation,
writes a change event and an audit event. A published module is never edited: the first change to it inside a draft
creates its next revision as a draft owned by that draft (copy-on-write). A changed question is a **new
`question_revision`** (insert-only); earlier versions keep their exact text. Conditions accept only the S0 predicate
language (`fact`/`equals`, `risk_band_in`, `all`) over an allowlist of approved facts and values (product family, ILP,
selling channel, premium frequency, SBQ band); fact mappings only `premium_term_years` and `premium_amount`. Expected-
answer policies must fit the answer type (exact boolean ↔ yes/no with an expected value; numeric match ↔ numeric with
an approved fact; acknowledgement ↔ acknowledgement; narrative review ↔ free text).

**Validation** (errors block submission; warnings inform the checker): no sections, empty section, duplicate question
code across sections, invalid condition or question configuration (errors); mandatory question without a control,
mandatory collect-only question, conditional common module, exact-audio delivery without an approvable audio asset,
no mandatory question (warnings).

**Lifecycle.** Submit (author/editor, change summary) validates, freezes a full manifest (`call360.script-manifest/2`:
every question's content and its control links, plus the section and module structure) and its SHA-256, and locks the
content. Review (`script.approve`, not a maker, reason required): APPROVE re-checks the manifest against the rows;
REQUEST_CHANGES returns it to DRAFT. Publish (`script.publish`, not a maker): re-checks the manifest, publishes the
draft's modules and the version together, effective now, optionally supersedes the family's published version (which
keeps its content and checksum and gets `effective_to`). Self-review and self-publish attempts are refused and audited
(`SCRIPT.REVIEW_DENIED`, `SCRIPT.PUBLISH_DENIED`).

**APIs** (all CSRF-protected writes, rate-limited at 240/min per author, market-scoped, audited): `POST /scripts`,
`POST /scripts/{id}/drafts`, `POST|PATCH|DELETE /script-versions/{id}/sections…`, `POST …/sections/reorder`,
`POST|PUT|DELETE …/sections/{sid}/questions…`, `POST …/questions/reorder`, `PUT …/questions/{code}/controls`,
`POST …/validate`, `POST …/submit`, `POST …/review`, `POST …/publish`; reads `GET …/history`, `GET …/diff?against=`,
`GET /question-bank`, `GET /script-authoring/options`. `GET /script-versions/{id}` gains row ids, `row_version`,
makers, display names and the controls source (frozen manifest or live). OpenAPI SHA-256
`d35e791e04be538bd6d0d99e224133319d3f45e038035e7fcaa172eef8bf0ea8`.

**Frontend (Script Studio).** Library: "New script" (script.edit). Script Detail: "New draft version"; tabs
**Edit questions** (draft editor: add section from a new or published module with an inclusion-condition builder, section
settings, move up/down, remove with inline confirmation; add a new question or reuse from the question bank, full
question form — wording, intent, category, answer type, delivery mode, expected-answer policy, expected answer, fact
mapping, choice options, mandatory, evidence required, re-prompts, variants, unacceptable outcomes, not-applicable and
asked-when conditions, escalation reference, change reason — controls and regulatory-reference links; validate panel
and submit with a change summary), **Review & publish** (lifecycle steps, makers who cannot approve, reviewer, manifest
checksum, approve / return for changes with a reason, publish with an explicit supersede choice), **Version diff**

## S2-A known limitations and open items

- Decisions D-54…D-57 are implemented as proposed and need confirmation. `SC_CHECKER` is a synthetic local role; real
  S&C checker identities come with enterprise SSO (S5). ADMIN can still manage group memberships (it could put a person
  into the checker group); maker-checker still holds because makers can never approve their own versions.
- No scheduling (future effective dates), withdrawal or rollback; publish is effective immediately. No simulator,
  regression gate or impact analysis; no language variants; branching is limited to simple asked-when / not-applicable
  conditions.
- Control links are concept-level (`question_bank_item`): a link changed in one draft is visible in other drafts of
  the same question; published versions are protected by their frozen manifests. Seeded S0 manifests did not freeze
  control links, so the diff and detail show live links for them.
- Every question save creates a new question revision (history is complete, numbering grows with edits). Discarding a
  whole draft is not offered (a draft can be emptied; drafts of unpublished families remain listed).
- The draft editor saves each change immediately (no batch "save" of several edits); concurrent editors are protected
  by the row-version token, not merged.
- Publishing a new version of the seeded `SALES_VERIFICATION_SG` family would change seeded rows (supersession) and so
  the seed digest; the demo therefore used a new family. Assignment rules still target seeded versions; rule editing
  and assignment are S2-B/S2-C.

**Scope** — SUR-010 (simulation workbench) over the existing S2-D / S2-D.1 controller: interactive simulation of draft

**Scenario model** (structured data, never code; `scenario_runner.py`, `simulation_workbench.py`):
- Facts: the four approved condition facts (product family, ILP, sales channel, premium frequency) and the SBQ band —

## S2-E known limitations

- Scenario facts cover the approved applicability facts and SBQ band only; numeric answers are free values (the
  controller does not evaluate expected answers — S3).
- The AFFIRMATIVE default answers 1 for numeric items and the first option for choices; it exists to keep scenarios
  short, and is visible per item in the response log.
- Coverage is structural (paths through the controller), never a compliance or readiness measure; lifecycle paths are
  derived from configuration, so a path the script cannot take is not listed.
- Batch runs execute synchronously (limit 50 scenarios per run); there is no scheduling or regression suite yet.
- A scenario stays within one script family; comparing families is not supported.
- Development state: draft **SG_LIFECYCLE_DEMO v1.1** (recording refusal terminates) remains open in Script Studio for
  the owner to keep, submit or abandon; rule `S2D1-LIFECYCLE-DEMO` remains published (D-69).
