**Requirements:** VOICE-007 (consent / purpose gate), VOICE-008 (input and output tracks, capture status, manifest),
VOICE-010 (gaps marked, never backfilled), EVD-001 (media outside the database, metadata in it, authorised

Out of scope: transcripts and playback UI (S1-D), GPT-Live and WebRTC (S1-E), any compliance or identity outcome.

**Owner decisions requested at S1-C acceptance (implemented as proposed; not approved policy):**

- **D-45 Test recording consent.** No approved consent wording or policy exists (BRD DEC-004 "consent gate in demo;
  actual policy set by Legal/Privacy"). S1-C uses a **test-only notice** (version `S1C-TEST-1`, shown verbatim and
  hashed), which is not AIA/MAS consent language. The signed-in operator, the only speaker in a synthetic test,
  decides before the session starts; **the default is Do not record**. Microphone permission is never taken as
  consent. The decision, notice version and SHA-256, actor and server time are stored in the insert-only session
  ledger. A resumed session keeps its decision. There is no mid-session change: to withdraw, the operator stops the
  session (recording ends with it).
- **D-46 Recording access.** The reserved permission `recording.read` (alias `RECORDING_READ`) is activated for S1
  and granted to the **USER** role only; ADMIN keeps the ADR-0004 segregation and does not receive it. Audio retrieval
  needs `recording.read` + Singapore scope; every retrieval (and every denial) is audited (`RECORDING.ACCESSED` /
  `RECORDING.ACCESS_DENIED`). Recording metadata (status, coverage, gaps, checksums) is visible with `case.read`;
  object keys and storage paths are never returned by any API.
- **D-47 Local storage and retention.** Audio chunks are stored outside the database and outside the repositories in
  a local encrypted object store (AES-256-GCM per object, separate `RECORDING_ENCRYPTION_KEY`, object key bound as
  associated data). Retention is a local development setting `RECORDING_RETENTION_HOURS` (default 168 h), not a
  policy (DEC-015 pending). Expiry deletes the audio objects only; the asset, chunk manifest, checksums, ledger event
  `RECORDING_PURGED` and audit stay. No production retention period is assumed.
- **D-48 Test sessions in operational metrics.** Every S1 browser session (transport `BROWSER`, origin
  `CALL360_RUNTIME`, mock provider) is labelled **test session** (`attempt_kind = TEST_SESSION`, derived, no schema
  change) in Call Detail, the voice APIs and the attempt list. KPI definitions are **not** changed: KPI-01 and KPI-02
  disclose how many counted rows are test sessions (`exclusions.test_sessions_in_numerator/denominator`). Whether
  test sessions should be excluded from attempt KPIs is a **business decision (K-5), not taken**.

**Capture model.** Recording is client-side, so it works unchanged when S1-E moves audio to WebRTC (the server will no
longer see the audio). Two independent tracks from one 16 kHz AudioContext clock: `MIC` (the echo-cancelled
microphone frames the browser sends) and `PROVIDER_PLAYBACK` (the provider audio as rendered by the browser's audio
graph after barge-in clearing — not acoustic speaker output and not the provider's generated stream). PCM16 LE mono
(`audio/L16;rate=16000`) in 2 s chunks, numbered per connection **segment** (segment *n* = the *n*-th connection of
the session) and per sequence, with the start sample within the segment, sample count and SHA-256 of the plaintext.
The recorder starts only when the server confirms an active recording on `session.ready`; frames captured earlier
(microphone opened before consent or before connection) are never buffered into a recording.

**Server rules.** `POST /voice/sessions` takes `recording_consent` (`GRANTED` needs the current notice version;
omitted = `DECLINED`). Chunks (`POST /voice/sessions/{id}/recording/chunks`, owner, CSRF, own rate limit): refused
unless consent was granted and the track is capturing or within the 30 s post-session upload window; segment must
exist; size ≤ 2 s; even length; sample count = bytes / 2; SHA-256 must match; audio may not claim more time than has
elapsed since the segment started (no fabricated or pre-segment audio); a repeated chunk with the same checksum is
an idempotent no-op, a different checksum is a conflict (no overwrite). Object keys are generated by the server
(`<attempt>/<track>/<segment>-<seq>.c360`), written exclusively (`O_EXCL`) and never accepted from the client.
`POST …/recording/close` carries the browser's per-segment manifest (chunks produced, chunks it could not upload,
close reason such as `STOPPED`, `MIC_DEVICE_LOST`, `CONNECTION_LOST`).

**Finalisation and states.** When the session ends, tracks go to `UPLOADING`; a track is finalised as soon as every
segment is closed and every declared chunk has arrived, or by the sweeper after the upload window. Coverage is
computed, never assumed: missing sequence numbers (`MISSING` or `UPLOAD_FAILED`), sample discontinuities
(`DISCONTINUITY`), the time between segments (`SESSION_INTERRUPTED`) and an unconfirmed end (`END_NOT_CONFIRMED`) are
gaps. No gap is filled. Per track: `media_status` `AVAILABLE` with coverage `COMPLETE` or `PARTIAL`, or `FAILED` when
nothing arrived. Session `media_status` (approved vocabulary) is `NOT_REQUIRED` (declined), `CAPTURING`, `UPLOADING`,
`AVAILABLE`, `FAILED` or `PURGED`. The API derives the owner's labels:

| Recording status (API) | Meaning | Stored basis |
|---|---|---|
| `NOT_RECORDED` | Consent declined or never connected | no `media_asset`; session `NOT_REQUIRED` |
| `RECORDING` | Capture or upload in progress | track `CAPTURING` / `UPLOADING` |
| `COMPLETE` | Both tracks available, no gap | both `AVAILABLE` + coverage `COMPLETE` |
| `PARTIAL` | Some audio stored, with gaps or one track failed | ≥1 `AVAILABLE`, any gap or a `FAILED` track |
| `FAILED` | Consent granted but no audio stored | all tracks `FAILED` |
| `PURGED` | Audio removed at local retention expiry | tracks `PURGED`; metadata kept |

**Schema (migration `0013_recording`).** `media_asset` (defined in S0_DATA_MODEL, deferred to S1): one row per track
per session; mutable lifecycle columns; identity, consent and (once set) checksums immutable; never deleted.
`media_chunk`: insert-only chunk manifest (segment, seq, start sample, sample count, bytes, SHA-256, server object
key). `session_event` gains `RECORDING_CONSENT_GRANTED`, `RECORDING_CONSENT_DECLINED`, `RECORDING_STARTED`,
`RECORDING_TRACK_CLOSED`, `RECORDING_FINALIZED`, `RECORDING_PURGED`. `recording.read` activated (D-46).

**APIs.** `GET /voice/preflight` (recording capability, notice, retention); `POST /voice/sessions` (consent);
`POST /voice/sessions/{id}/recording/chunks`; `POST /voice/sessions/{id}/recording/close`;
`GET /voice/sessions/{id}` (recording summary); `GET /sessions/{id}/media` (API-046: evidence availability
`AVAILABLE`/`RESTRICTED`/`NOT_AVAILABLE`/`FAILED`, tracks, gaps, checksums); `GET /sessions/{id}/media/{track}/audio`
(`recording.read`, audited; WAV of the stored chunks in order — gaps are listed, not filled; SHA-256 header equal to
the stored content checksum).

## S1-D proposal — Transcript and playback (2026-11-17; authorised by `IMPLEMENT S1-D`; as built below)

### Requirements

access audit, S1 subset). BRD rules applied: §2.4 provenance class "recognised transcript" kept distinct from system

CORRECTED_BY_ADDENDUM | UNAVAILABLE` (already on `conversation_session.transcript_status`).

Out of scope: live transcript in Voice Studio (S1-E), GPT-Live, answer extraction (S2, COMP-001), human correction
(S3, SCR-021), transcript search (S3, SEARCH-009), quality scoring (S3, VOICE-013), compliance or identity outcomes.

### Is a speech-to-text component needed? Yes — for real speech

- The mock provider recognises nothing: it uses an energy detector for barge-in and replays a fixed message. Nothing
  in the stack produces recognised text today.
- Its fixed message (`FIXED_MESSAGE` in `app/voice/mock.py`) is **system text**, not a transcript. Displaying it as
  the transcript of the provider track would claim what was audibly rendered (barge-in truncates it) — that is
  inventing recognised text. It may appear only as labelled reference text ("scheduled mock message").
- Browser Web Speech API: rejected — in Chrome it sends audio to a third-party service outside Call360's control,
  gives no stable timestamps or confidence, and cannot run on stored evidence.
- Cloud STT (e.g. OpenAI, Azure, Google): rejected for S1-D — needs a provider key, a data-transfer decision and vendor
  approval; GPT-Live's own input transcription arrives with S1-E as a *separate provenance source*.

**Recommendation (D-49): one local, offline engine behind a `TranscriptionEngine` interface — `faster-whisper`
(CTranslate2 Whisper) with the English `small.en` model, int8 on CPU, run as a post-session batch job over the stored,
finalised recording.** Audio never leaves the machine; the model name, revision and file SHA-256 are pinned and stored
on every run; outputs carry per-segment and per-word confidence; its built-in Silero VAD and Whisper's
`no_speech_prob` let silence stay silence. Cost: a backend dependency (`faster-whisper`, permissive licence) and a
one-time model download (~480 MB from Hugging Face; `base.en` ~150 MB is the lighter fallback) — the download needs
owner permission. Expected speed on this Apple-silicon machine: faster than real time; a short test session should be
transcribed within seconds of finalisation (to be measured, not assumed).

### Rules that keep recognised text honest

1. Only engine output is transcript text. No text is generated from the script, the fixed message, the case or a model
   prompt. Empty or failed recognition stays empty with an explicit marker.
2. Both tracks are transcribed independently: `MIC` → speaker **"Caller (browser microphone)"**; `PROVIDER_PLAYBACK` →
   **"Mock voice (Call360 test)"**. Speaker labels come from the track (channel separation), not diarisation and not
   identity (identity stays `NOT_PERFORMED`).
3. Engine settings that limit hallucination: VAD filter on, `condition_on_previous_text = false`, temperature 0
   fallback chain as pinned params; segments with compression ratio > 2.4 or `no_speech_prob` > 0.6 with low log-prob
   are not shown as text (kind `NO_SPEECH`, text discarded, metrics kept).
4. Uncertainty is shown, never smoothed: segment `LOW_CONFIDENCE` when mean log-prob < −1.0; words with probability
   < 0.5 marked uncertain. Thresholds are development values (D-52), stored with every run.
5. Recording gaps become `AUDIO_GAP` markers in the transcript ("audio missing — not transcribed"); nothing is
   transcribed across a gap; a track that is `PARTIAL` makes the transcript at best `PARTIAL`.
6. The provider track gets a measurable sanity check: the share of its recognised words that match the scheduled
   fixed message in order (precision — barge-in legitimately truncates the message, so missing words are not errors),
   stored as a run metric and shown as "engine check", never used to change text.
7. Runs are immutable: a re-run (new model or params) is a new revision; the first stays visible (EVD-004).
8. Overlap of caller speech with mock playback (barge-in or echo) is flagged `OVERLAPS_MOCK_PLAYBACK` by time only;
   the text is not altered. Headphones are recommended for acceptance tests (echo cancellation is on).

### Time model and playback linkage

- Canonical time is **recording time**: (track, recording segment, sample offset) on the shared 16 kHz clock. MIC and
  PROVIDER_PLAYBACK share the segment start, so the same offset is the same moment on both tracks.
- The evidence WAV concatenates stored chunks, so after a gap its playback offset is earlier than recording time.
  S1-D adds a server-computed **timeline map** (each stored chunk span: recording position ↔ WAV byte/sample offset,
  plus gap spans). Transcript segments store recording time; the player maps through the timeline. The evidence WAV
  is not changed and silence is never inserted into it.
- A transcript segment links to: session, attempt, track asset (`asset_ref`, `content_sha256` of the transcribed
  audio), recording segment and sample range, and the `RECORDING_FINALIZED` session event that triggered the run
  (VOICE-009 "source event").

### Data model (migration `0014_transcript`)

- `transcript_run` (insert + status updates, guarded): session, attempt, track, `media_asset_id`, input
  `content_sha256`, engine, engine version, model id, model SHA-256, params JSON, thresholds, status
  `PENDING | RUNNING | DONE | FAILED`, error code, timings, metrics (duration transcribed, segment counts by kind,
  provider-track engine check), `revision`.
- `transcript_segment` (insert-only, already a planned canonical table): run, ordinal, recording segment, start/end
  sample, kind `SPEECH | NO_SPEECH | AUDIO_GAP`, confidence class `NORMAL | LOW_CONFIDENCE`, metrics (avg log-prob,
  no-speech prob, compression ratio), flags, text and per-word timings/probabilities **encrypted** with the recording
  key (AES-256-GCM, same store discipline as audio), `text_sha256`.
- Session `transcript_status` is derived and written: `UNAVAILABLE` (no recording, declined, failed, purged, engine not
  configured), `PENDING` (run queued/running), `FINALIZED` (both tracks done, complete coverage, no low-confidence
  share above threshold), `PARTIAL` (gaps, one track failed or a partial recording), `QUALITY_FLAGGED` (low-confidence
  share above threshold). `CORRECTED_BY_ADDENDUM` unused until S3.
- Retention follows the audio: the 168 h purge also deletes transcript text, keeping run/segment metadata and hashes.
- New session events (metadata only): `TRANSCRIPT_STARTED`, `TRANSCRIPT_COMPLETED`, `TRANSCRIPT_FAILED`.
- `answer_observation` stage lock (`transcript_segment_ids` empty) stays until S2.

### Processing

A backend worker picks `PENDING` runs created when a recording finalises (and by the existing sweeper, so a restart
resumes). It decrypts the track in memory, verifies `content_sha256` first (mismatch → `FAILED
RECORDING_INTEGRITY_FAILED`), transcribes in a worker thread with a concurrency of 1, and writes segments in one
transaction. Never inside a request; never on unconsented, purged or unfinalised audio.

### APIs

- `GET /api/v1/sessions/{id}/transcript` — `transcript.sensitive.read`: status, runs (engine/model provenance,
  metrics), segments with speaker, recording-time and playback-time ranges, kind, confidence, flags, text and word
  uncertainty. Audited `TRANSCRIPT.ACCESSED` / `ACCESS_DENIED`. Without the permission: status and counts only.
- `GET /api/v1/sessions/{id}/media/{track}/timeline` — `recording.read`: timeline map and gaps (no storage paths).
- Playback reuses `GET …/media/{track}/audio` (`recording.read`), adding a `purpose=PLAYBACK|DOWNLOAD` query value
  recorded in the existing `RECORDING.ACCESSED` audit, plus `Cache-Control: no-store`.
- Malaysian or out-of-scope sessions: audited 404, as today. Transcript text never appears in logs, session events,
  case-event summaries, search or error messages.

### Frontend (Call Detail centre column, BRD §6 layout)

- Player: one synchronised transport over both decoded tracks (Web Audio, single clock) with Mic / Mock voice
  mute toggles, play/pause, ±5 s, seek bar showing gap spans; keyboard operable with labelled controls. Audio is
  fetched once per view into memory (blob revoked on leave), never cached.
- Transcript list in time order across both speakers: speaker label, `mm:ss` recording time, text with uncertain words
  marked (not colour alone), `Low confidence` badge, explicit markers "No speech recognised", "Audio missing — not
  transcribed", "Transcription failed", and engine/model provenance with the "engine check" result. Selecting a
  segment seeks the player; the playing segment is highlighted with `aria-current`.
- States: transcript pending (polls), unavailable with reason (declined, not recorded, purged, engine not configured),
  no access (status only), integrity failure. Voice Studio shows only "Transcript: pending / ready in Call Detail".

8. Authorisation: USER with permission reads text; ADMIN and users without it get status only; every access audited;

10. UI: segment click seeks both tracks; gap spans shown; keyboard and screen-reader operation; axe clean; 375–1440 px.

  authorisation to spend"; managers may change them (reason required, insert-only change history; per experiment ≤ daily
  ≤ overall; interactive 5–300 s; idle 2–60 s). The per-experiment limit also caps one interactive session. Days are
  Asia/Singapore days.
- **D-91 Reservation and reconciliation.** Before a metered session or experiment exists, the server — holding a
  per-class advisory lock — checks the kill switch, per-experiment, daily and overall limits and concurrency (held
  reservations ≤ maximum concurrent) and reserves the *estimated maximum* (both directions for the whole maximum
  duration). At the end it reconciles with the measured audio (never above the maximum duration) or the trials' measured
  costs; reservations are immutable except their one closing. Unknown cost → refused (`COST_UNKNOWN`, fail closed). At
  restart open sessions reconcile at the reserved maximum (conservative).
- **D-92 Evaluation.** Deterministic only (`call360.voicelab-eval/1`): word alignment of the expected statement against
  the provider's own text (*said*) and the local faster-whisper transcript of the provider audio (*heard*); exact match,
  added / omitted / substituted words, WER; deviations attributed as *suspected speech deviation* (also in the provider
  text), *suspected transcription error* (provider text matches — listen), *unattributed* (no provider text) or
  *provider text only*; structured answers compared field by field; first-audio and interruption latency, duration and
  cost. **Exact wording is judged only on the independent transcript** — the provider's own text is a claim, not proof
  (no audio → NOT_MEASURED → needs human review). Missing measurements are never a pass. Expected behaviour always needs
  human assessment (no LLM judge).
- **D-93 Mock experiment content.** The mock provider's spoken text is the test case's "mock output" (default: the
  expected statement) and its audio is the case's optional synthetic WAV fixture (16 kHz mono, ≤ 30 s); timing comes from
  running the real S1-A mock provider in-process with a synthetic barge-in at 600 ms; structured answers come from a
  labelled deterministic keyword extraction (`MOCK_KEYWORD_EXTRACTION/1`). None of this represents a real provider.
- **D-94 Interactive playground.** Same browser audio client and mock provider as Voice Studio; server-side recording
  (microphone as received, provider audio as sent at its send time) only when chosen per session; independent
  post-session transcript; server-measured first-audio and interruption latency; provider event trace (insert-only);

## S1-E.2 design decisions (proposed — need owner confirmation)

- **D-95 Transport.** Server-side primary WebSocket per Voice Lab session (browser ⇄ Call360 ⇄ GPT-Live), reusing the
  S1-A browser WebSocket media path unchanged; audio format `audio/pcm` 16 kHz both ways (supported by GPT-Live, so no
  resampling). The key is read only by the backend (`VOICE_LAB_OPENAI_API_KEY`) and never returned, logged or sent to
  the browser. WebRTC and the ephemeral-key browser path are not used.
- **D-96 Interruption.** GPT-Live documents no speech-started or cancel events; the adapter applies the documented
  client-side policy: the S1-A local VAD clears browser playback and drops provider audio until the caller's turn ends.
  Response boundaries are inferred from audio gaps (≥ 600 ms; done after 800 ms without audio).
- **D-97 Instructions and delegation.** Per-turn instructions are appended (`session.instructions.append`,
  session-wide) after each caller turn; Playground instructions likewise. Client delegation (`delegation: {type:
  "client"}`) is answered with `session.commentary.append` by a deterministic Python responder
  (`DETERMINISTIC_PYTHON/1`: fixed synthetic sentences chosen by keyword from the latest caller transcript) — no LLM,
  tool, backend model, LangChain, LangGraph, DSPy or network call.
- **D-98 Paid gates.** A paid (GPT_LIVE) session needs, at creation and in one transaction: server configuration
  (`VOICE_LAB_GPT_LIVE_MODE=LIVE` + key), the manager's paid switch (`lab_control.paid_enabled`, off by default,
  audited), an ISSUED **single-use smoke-test authorisation** (provider, model, voice, ≤ 120 s, its own USD maximum,
  expiry ≤ 72 h, one at a time) issued by a Voice Lab manager and executed by a **different** user with Voice Lab access
  (database four-eyes CHECK), consumed by that session (unique), and the PAID budget (limits and one concurrent paid
  session). Paid experiments stay impossible (CHECK). Revocation and expiry are supported.
- **D-99 Termination and usage.** The server timer (the session's maximum, ≤ the authorisation's) ends the session
  independently of the browser; on timeout, Stop, emergency stop, browser disconnect, provider error or protocol error
  the adapter sends `session.close` and waits (`VOICE_LAB_CLOSE_TIMEOUT_S`, default 5 s) for `session.closed`. Only a
  received `session.closed` with usage seconds settles the reservation (cost = seconds × USD 0.05 / 60, rounded up to
  USD 0.0001). No connection → nothing to pay. Otherwise the termination is UNCONFIRMED and the reservation stays HELD
  at its maximum (blocking further paid sessions) until a manager records the provider-reported usage or closes the
  orphan over the documented sideband (`…/attach` → `session.close` → `session.closed`). A process restart treats any
  connected GPT-Live session as UNCONFIRMED. No automatic reconnection or retry.
- **D-100 Synthetic GPT-Live mock.** Provider `GPT_LIVE_MOCK` (SIMULATED class): the same adapter against a mocked
  protocol server on loopback (`VOICE_LAB_GPT_LIVE_MOCK_URL`; `call360 gpt-live-mock`), metered at the verified rate as
  synthetic metering — never money. Tests may point the real provider at the loopback mock only in `APP_ENV=test`;
  otherwise the only allowed remote host is `api.openai.com`.
- **D-101 Retention.** The 168-hour local retention (`RECORDING_RETENTION_HOURS`) deletes Voice Lab session audio
  objects and blanks session transcripts (independent and provider transcripts); rows, checksums, metrics, events,
  costs and evaluation history are kept; synthetic golden-dataset fixtures are test assets and are kept. The event trace
  never contains transcript text.
- **D-102 Speech results.** Each trial reports an automated speech result — automated transcript match, suspected
  speech deviation, suspected transcription error, insufficient audio evidence — and a person who listened may record a
  human-confirmed result (as expected / deviation / inconclusive; insert-only). No text claims that transcription proves
  verbatim delivery.
